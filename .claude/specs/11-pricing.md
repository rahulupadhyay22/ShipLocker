# Spec: Free vs. Premium Membership & Trunk Assist Pricing

## Overview

Per `CamelTrunk_Free_vs_Premium_and_Trunk_Assist_Functionality.MD` (V1), Premium (`Locker.plan_type='paid'`) accounts get three automatic, no-coupon discounts on CamelTrunk's own revenue lines — never on product value, local delivery, taxes, or other third-party costs:

- **25% off** the TrunkAssist service charge (`PersonalShopQuotation.service_fee_amount`, purchase-type quotations).
- **5% off** the eligible international shipping charge (`Shipment.shipping_cost`), recomputed on every read against the locker's *current* plan — not locked in at the moment a tier is picked — so an upgrade before payment is reflected without the customer having to re-select a tier.
- **FREE** consolidation fee (`Shipment.consolidation_fee`) and any future "basic service" configured the same way.
- **20% off** the daily storage charge (`BatchCharge.amount`) once a batch's free-storage period has run out and it starts accruing daily charges — i.e. once the "30 days is extended" (spec 09's Premium 30-day free period) has actually been used up. This is a discount on the *rate*, layered at the moment each `BatchCharge` is created — it does not touch, replace, or duplicate `lookup_daily_rate`'s rate table (see Depends on / Rules for exactly how this stays a single source of truth).

`Locker.plan_type` (`free`/`paid`) already exists — added by `09-storage-fee.md` and already driving storage benefits (30 unconditional free days for `paid`, vs. 20 days + 3 annual passes for `free`, via `apps/locker/services/batch_billing.py`). This spec **does** make one small, additive touch to `apps/locker/services/batch_billing.py::run_daily_billing` (the 20% storage discount above) — everything else about batch/storage lifecycle (free-period length, quota, grace period, abandonment) is untouched, and `lookup_daily_rate` stays the sole source of truth for the underlying rate table; this spec only multiplies its output by a Premium discount factor at the point a charge is actually created, exactly the same layering pattern the other three discounts use on top of `ServiceCharge`/`ShippingRate`. This spec also (a) surfaces the account-type badge wherever storage charges already display (doc §3), and (b) wires the TrunkAssist/shipping/consolidation discounts above, which spec 09 never touched.

No new membership model, no new app. `Locker.plan_type` is the single Free/Premium flag; discount math is added as small pure methods on `Locker` itself, called from the existing quotation/shipment/consolidation code paths at the moment each charge is computed or displayed — never baked into a background job.

**Premium subscription: ₹2,999/year, self-serve Razorpay checkout.** This price/cadence was previously undefined in the source pricing doc; it's now fixed by explicit product decision, not derived from the doc. A customer pays via a new `CreatePremiumSubscriptionOrderView` → the existing `VerifyPaymentView`/`RazorpayWebhookView` (a fourth `Payment.payment_type` branch, `'premium_subscription'`) → `Locker.plan_type='paid'` and `Locker.premium_expires_at` set/extended by 365 days. Renewal is **not silently auto-charged** — Razorpay isn't wired for recurring auto-debit anywhere in this codebase (matches spec 09's existing "No gateway auto-debit" rule for storage payments) — the customer re-visits the same checkout to renew.

**Expiry is tracked and enforced, reusing spec 09's grace-period machinery almost entirely as-is** — `Locker.payment_grace_until`'s own help text already says *"Set when a paid-plan renewal fails"*, meaning spec 09 built this specifically anticipating a premium-renewal use case that nothing called yet. A new daily management command (`sync_premium_renewals`, mirroring `sync_storage_batches`'s existing structure) does, per Premium `Locker`:
1. **Reminder** — `days_until_expiry == 7` and not already in grace: send a renewal-reminder notification (`apps/notifications/signals.py::send_notification`, new WhatsApp template name).
2. **Expiry → grace** — `premium_expires_at` has passed and `payment_grace_until` is `None`: call the existing `batch_billing.enter_grace_period(locker, today)` unmodified — this is exactly the 7-day grace window spec 09 already built for this scenario.
3. **Grace exhausted → auto-downgrade** — `payment_grace_until` has passed with no renewal payment: call the existing `batch_billing.resolve_grace_period(locker, today, payment_succeeded=False)` unmodified — this already runs `apply_downgrade` (resets `plan_type='free'`, recalculates `UserQuota` correctly per spec 09's Fix #2) and recalculates any batches that were sitting in `pending` status during the grace window. This spec only adds clearing `locker.premium_expires_at = None` afterward (a field spec 09 doesn't know about).

A renewal payment landing *during* an active grace period calls `resolve_grace_period(locker, today, payment_succeeded=True)` (also unmodified) instead of a bespoke success path — that function already correctly resolves any `pending` batches back to normal terms.

No packing-fee or "other basic services" charge exists anywhere in the codebase today (only `consolidation_fee` is a chargeable "basic service" per `ServiceCharge`) — nothing to make free beyond consolidation; the pattern (`locker.premium_free_service()`) is documented so a future packing fee plugs into it the same way.

## Model changes

**`apps/accounts/models.py` — `Locker`:**
- `is_premium` property: `self.plan_type == 'paid'`. Replaces every ad-hoc `locker.plan_type == 'paid'` check this spec would otherwise scatter.
- `PREMIUM_SERVICE_FEE_DISCOUNT_RATE = Decimal('0.25')`, `PREMIUM_SHIPPING_DISCOUNT_RATE = Decimal('0.05')`, `PREMIUM_STORAGE_DISCOUNT_RATE = Decimal('0.20')` module-level constants.
- `apply_service_fee_discount(self, standard_amount)` → `(final_amount, discount_amount)`. Returns `(standard_amount, Decimal('0.00'))` unchanged when `not self.is_premium` or `standard_amount is None`. Callers pass only the CamelTrunk service-charge component in — never product value/local delivery (doc §2).
- `apply_shipping_discount(self, standard_amount)` → `(final_amount, discount_amount)`. Same shape, 5% rate.
- `apply_storage_discount(self, standard_amount)` → `(final_amount, discount_amount)`. Same shape, 20% rate. Called once per batch per day, from `batch_billing.run_daily_billing`, on that day's `lookup_daily_rate(...)` output — never from anywhere in `apps/locker/models.py` or `UserQuota`/free-period logic, which stay entirely untouched (see Rules).
- `premium_free_service(self)` → `bool`, alias for `is_premium`, named for its call sites (`if locker.premium_free_service(): fee = 0`) so a future packing-fee or other-basic-service call site reads intent, not a raw plan check.
- `premium_expires_at = models.DateField(null=True, blank=True)` — **new field.** Set/extended by 365 days on every successful `premium_subscription` `Payment` (see `VerifyPaymentView`/`RazorpayWebhookView` below) and by the `LockerAdmin.save_model` manual-toggle path (Phase A of the plan), so a staff-comped Premium account is tracked by the same renewal job as a paid one. Cleared (`None`) on auto-downgrade. `None` on a `plan_type='free'` locker means nothing (expected); `None` on a `plan_type='paid'` locker is a legacy/comped edge case the daily renewal job simply skips (never expires it) rather than crashing on a missing date.

**Migration:** one migration in `apps/accounts` for `premium_expires_at` (the `is_premium`/`apply_*_discount`/`premium_free_service` additions above stay migration-free — plain methods/properties).

**`apps/notifications/models.py` — `AppSettings`:**
- `premium_annual_price = models.DecimalField(max_digits=10, decimal_places=2, default=Decimal('2999.00'))` — admin-editable, same "config lives in `AppSettings`, not a hardcoded constant" pattern this model already uses for `razorpay_key_id`/warehouse address/everything else revenue-relevant. `CreatePremiumSubscriptionOrderView` reads `AppSettings.get_settings().premium_annual_price` at order-creation time — a future price change takes effect without a deploy, exactly like every other `AppSettings` field.

**`apps/payments/models.py` — `Payment`:**
- `PAYMENT_TYPE_CHOICES` gains `('premium_subscription', 'Premium Subscription')` — a fourth branch alongside the existing `shipment`/`storage_batch` (both already nullable/unrelated FKs, per the existing model) — a `premium_subscription` payment has `shipment=None`, `personal_shop_request=None`, identified purely by `payment_type` and `user`, same shape `storage_batch` already uses.

**`apps/personal_shop/models.py` — `PersonalShopQuotation`:**
- `service_fee_standard_amount = models.DecimalField(max_digits=10, decimal_places=2, default=0)` — **this is now the editable field.** It holds the pre-discount fee staff actually set (defaulted from `pricing.suggested_service_fee()`, but staff may override it — same as today). `service_fee_amount` (existing field) becomes **read-only, server-computed only** — see Files to change/Rules for how `save_related` derives it. This split is what makes the discount idempotent: there is no field that is both "what staff typed" and "what must already be discounted," so there is nothing to accidentally re-discount on a second save.
- `service_fee_manual_override = models.BooleanField(default=False)` — set by `save_related` (server-side, not client-trusted), but **only re-evaluated when `service_fee_standard_amount` was actually touched in that submission** (`'service_fee_standard_amount' in form.changed_data`, Django's own field-diff), comparing the newly-submitted value against `pricing.suggested_service_fee(...)` computed fresh at that moment. If the field wasn't touched this save, `service_fee_manual_override` is left exactly as it was. **This is deliberate, not an oversight:** re-deriving `suggested` fresh on *every* save (regardless of whether the field changed) mislabels an untouched old quotation as "manually overridden" the instant the underlying `ServiceCharge` catalog price changes later, since `suggested` would no longer match a value nobody edited. Gating on `form.changed_data` is what prevents that. Pure audit trail (doc §10: "store original fee... and reason") — never read by any pricing logic, only displayed in `list_display`/detail for staff visibility into whether a fee was auto-suggested or hand-typed.
- `premium_discount_amount` property: `max(Decimal('0.00'), self.service_fee_standard_amount - self.service_fee_amount)` — the `max(..., 0)` guard means a non-`purchase` quotation (where both fields sit at their `default=0` and are simply unused) or any future data anomaly never renders a negative "discount" in the template; it silently reads as no discount instead of a confusing negative number.
- `Meta.permissions` gains `('override_service_fee', 'Can override the auto-suggested TrunkAssist service fee')` — a new, separate permission (same shape as `PersonalShopRequest.Meta.permissions`'s existing `mark_work_started` from spec 10, which already gates a different money-affecting admin action identically) gating *who* may set `service_fee_standard_amount` away from the catalog suggestion. Without this, any staff member with plain `change_personalshopquotation` access could set an arbitrary fee with no additional check — see `save_related` below for the enforcement.

**`apps/shipments/models.py` — `Shipment`:**
- `shipping_cost_standard = models.DecimalField(max_digits=10, decimal_places=2, null=True, blank=True)` — pre-discount snapshot, mirrors `shipping_cost`'s nullability (unset until a service tier is picked).
- `consolidation_fee_standard = models.DecimalField(max_digits=10, decimal_places=2, null=True, blank=True)` — pre-discount snapshot, set once at shipment creation alongside `consolidation_fee` (mirrors that field's own "locked in at creation" comment). Lets a Premium shipment's create/detail/order-history pages show "FREE with Premium — you saved ₹99" even though `consolidation_fee` itself is `0.00`.
- `shipping_discount_amount` / `consolidation_fee_discount_amount`: not stored — both are simple properties (`standard - final` when both are non-null, else `Decimal('0.00')`), same pattern as `PersonalShopQuotation.premium_discount_amount` above. No redundant field to keep in sync.
- `refresh_shipping_discount(self)` — new method on `Shipment`. While `payment_status != 'paid'` and `shipping_cost_standard` is set, recomputes `shipping_cost` from `shipping_cost_standard` against `self.user.locker.is_premium` (via `apply_shipping_discount`) and `.save(update_fields=['shipping_cost', 'updated_at'])` if it changed. No-ops once `payment_status == 'paid'` — a settled shipment's charged amount is a locked historical record, exactly like an approved `PersonalShopQuotation`'s `service_fee_amount` (see Rules). This is what makes the 5% discount recompute on read instead of being locked in at tier-selection time.

**`apps/payments/models.py` — `BatchCharge`:**
- `amount_standard = models.DecimalField(max_digits=10, decimal_places=2, null=True, blank=True)` — the pre-discount daily rate (`lookup_daily_rate(...)`'s raw output) snapshotted at charge-creation time, mirroring the `*_standard` snapshot pattern used on `PersonalShopQuotation`/`Shipment` above. `amount` (existing field) stays the *final, charged* figure — every existing reader (`BatchChargeAdmin`, the payment-summary aggregations in `apps/shipments/views.py::_payment_summary`/`apps/payments/views.py::CreatePaymentOrderView`) keeps summing/reading `amount` unchanged.
- `discount_amount` property: `max(Decimal('0.00'), self.amount_standard - self.amount)` if `amount_standard is not None` else `Decimal('0.00')` — same negative-guard shape as `PersonalShopQuotation.premium_discount_amount`, needed because pre-existing `BatchCharge` rows (created before this spec ships) have `amount_standard = NULL`.

**Migrations:**
- `apps/accounts/migrations/000X_locker_premium_expires_at.py`
- `apps/notifications/migrations/000X_appsettings_premium_annual_price.py`

    ```python
        # Only re-evaluate manual-override status when the editable field was

                    "Custom service fee reverted to the standard suggested amount — overriding it "
                    "requires the personal_shop.override_service_fee permission.",
                    level='warning',
                )
            obj.service_fee_manual_override = is_override
        # else: field untouched this submission — service_fee_manual_override
        # stays exactly what it already was; nothing to re-derive.

        locker = getattr(obj.request, 'locker', None)
        if locker is not None:
            obj.service_fee_amount, _discount = locker.apply_service_fee_discount(
                obj.service_fee_standard_amount
    ```

    ```python
        VerifyPaymentView and RazorpayWebhookView — kept in one place, same
    ```

    ```python
            ...
        elif payment.personal_shop_request:
            ...
        elif payment.payment_type == 'storage_batch':
            ...
        elif payment.payment_type == 'premium_subscription':
            _activate_premium_subscription(payment)
    ```

## Rules for implementation

- Use Django ORM only. No raw SQL unless absolutely necessary; parameterised queries only if raw SQL is unavoidable.
- Ownership mixins: no new routes/views are added — the modified views (`SelectShippingServiceView`, `PersonalShopQuotationView`, `CreatePersonalShopPaymentOrderView`, `CreateShipmentView`) already use `LockerOwnershipMixin`/`UserOwnershipMixin`/`SecureActionMixin` per the existing code; do not remove or weaken those.
- Security logging through the `security` logger: extend the existing "Service tier selected" and "Secure action" log lines in `SelectShippingServiceView`/`CreatePersonalShopPaymentOrderView` to include the discount amount applied, so a support investigation can see exactly what a customer was charged and why without cross-referencing `Locker.plan_type` history.
- CSS variables from `static/css/main.css` only for any new badge/CTA styling.
- Upload files to Supabase Storage — not applicable, no file uploads in this spec.
- Templates extend `templates/base.html` — all modified templates already do; no change to that.
- **`service_fee_amount` invariant, and why it's now read-only:** `PersonalShopQuotation.service_fee_amount` must always hold the *final, charged* amount, because `PersonalShopInvoiceService.generate_for_request` snapshots it verbatim into `PersonalShopInvoice.service_fee_amount` and `generate_pdf` prints it as the "TrunkAssist Service Fee" line — if that field ever held the pre-discount figure, the invoice's own line items would stop summing to its own total. Making it simultaneously "the field staff type into" and "the field that must already be discounted" is unfixably ambiguous — there is no way to tell, on a second save, whether the value sitting there is a fresh standard figure or an already-discounted one from the first save (an earlier draft of this spec tried to detect that with a `_loaded_service_fee_amount` comparison and never actually defined it — that approach is abandoned). The fix is structural, not conditional: `service_fee_standard_amount` is the **only** field staff edit (admin `readonly_fields` now includes `service_fee_amount`), and `service_fee_amount` is **unconditionally recomputed from `service_fee_standard_amount` on every `save_related` call**, never read back into itself. Saving the same quotation any number of times is therefore naturally idempotent — there is no "if changed" branch that can be wrong, because the derivation never depends on the field's own prior value. Verify this manually: save a quotation twice in admin with no changes and confirm `service_fee_amount`/`total_amount` are identical both times, and confirm the `service_fee_amount` input is disabled/read-only in the rendered admin form.
- **The 25% discount applies to `service_fee_amount` (purchase-type quotations) only** — not `research_fee_amount` or `travel_expense_amount`. `travel_expense_amount` is a pass-through third-party/travel cost (doc §2 explicitly excludes "other third-party expenses"). `research_fee_amount` is CamelTrunk's own revenue and a defensible read of §2 would include it, but this spec deliberately scopes the automatic discount to the ordinary purchase-flow service charge only, matching the doc's own worked example (§9: "₹500 standard service charge"), which is a purchase-type scenario. If the business wants research/expense-advance fees discounted too, that is a follow-up decision, not an oversight here.
- **Upgrade-before-payment recalculation (doc §10) is done by recomputing on read, not by a signal or cron job** — `PersonalShopQuotationView.get` and `CreatePersonalShopPaymentOrderView.post` both recompute `service_fee_amount` from `service_fee_standard_amount` against the quotation's *current* `locker.is_premium` immediately before use, mirroring the existing lazy-expiry-check pattern already in `PersonalShopQuotationView.get`. This guarantees the amount a customer sees on the quotation page is exactly what gets charged a moment later, even if they upgraded mid-session. Only `status == 'pending'` quotations are recomputed — an `approved` (already paid) quotation's `service_fee_amount` is a locked historical charge and must never change after payment.
- **The 5% shipping discount uses the same recompute-on-read shape, not a one-time calculation at tier selection.** `SelectShippingServiceView.post` still computes and stores `shipping_cost`/`shipping_cost_standard` once, at the moment a tier is picked — but that value is not treated as final. `Shipment.refresh_shipping_discount()` is called at every point `shipping_cost` is about to be shown or charged (`ShipmentDetailView.get_context_data`, `CreatePaymentOrderView.post`), and re-derives `shipping_cost` from the stored `shipping_cost_standard` against the locker's plan *at that moment*. A customer who selects a tier as Free, then upgrades to Premium before paying, sees and is charged the discounted price without re-selecting anything. Like the quotation, this recompute is disabled the instant `payment_status == 'paid'` — a settled shipment's `shipping_cost` is a locked historical charge, never recalculated afterward even if the locker later downgrades.
- `_get_consolidation_fee_amount(locker)` takes `locker` as a **required**, not defaulted, parameter — a call site that forgets to pass it must fail immediately (`TypeError`) rather than silently charging (or failing to discount) a Premium user. Use `getattr(request.user, 'locker', None)` at each call site and treat a missing locker as `is_premium=False` (same defensive pattern `_payment_summary` already uses — a payment-adjacent code path must never 500 on a missing relation).
- `Locker.apply_shipping_discount`/`apply_service_fee_discount` round with `.quantize(Decimal('0.01'), rounding=ROUND_HALF_UP)`, matching `SelectShippingServiceView.post`'s existing rounding convention for `price`.
- No new scheduled task, signal, or cron job for any of this — every discount is computed synchronously at the point a charge is created or displayed, consistent with `10-trunk-assist-service-charges.md`'s "read lazily wherever it matters" rule.
- **Storage discount scope, precisely:** the 20% storage discount is applied in exactly one place — `run_daily_billing`'s (and `_bill_retroactive`'s) call to `Locker.apply_storage_discount`, immediately after `lookup_daily_rate(...)` and immediately before `BatchCharge.objects.create(...)`. Do not add a `plan_type` field to `Batch`/`UserQuota`, do not touch `create_batch`/`add_parcel_to_batch`/`close_batch`/quota logic/grace-period logic/abandonment logic, and do not modify `lookup_daily_rate`'s rate table itself — that function's output stays the single source of truth for the *base* daily rate; this spec only multiplies it by a Premium factor at the point a charge is created, the same layering every other discount in this spec uses on top of its own base-pricing source (`ServiceCharge`, `ShippingRate`). "If 30 days is extended" (the phrase driving this addition) is naturally satisfied by *where* the discount is applied: `run_daily_billing` only reaches the `lookup_daily_rate`/charge-creation code path once a batch has already exhausted its free-storage period and become `active_chargeable` — the discount cannot fire during the free period itself because no `BatchCharge` is created then, so there's no separate "has the free period ended" condition to write.
- No new discount field is added to `Batch` or `UserQuota` — `BatchCharge.amount_standard` (a per-charge snapshot, one per day) is sufficient for the audit/display trail; a `Batch`-level field would imply a single fixed rate for the batch's whole lifetime, which isn't true (`lookup_daily_rate` varies by live parcel count day to day).
- **No silent recurring auto-debit.** Renewal always requires the customer to complete a fresh Razorpay checkout — matching spec 09's existing "no gateway auto-debit" rule for storage payments, and consistent with the fact that nothing in `RazorpayService` initiates a charge without an explicit `create_order` call from a user action. `sync_premium_renewals` never creates a `Payment` or calls `RazorpayService` itself — it only manages `payment_grace_until`/`plan_type`/notifications.
- **Reuse `enter_grace_period`/`resolve_grace_period`/`apply_upgrade` from `apps/locker/services/batch_billing.py` completely unmodified for the renewal lifecycle** — do not add a parallel "premium grace" concept or a second grace-period field. `Locker.payment_grace_until` is shared by both the storage-batch-payment-failure scenario spec 09 built it for and this spec's premium-renewal-failure scenario; both are, in fact, the same underlying event ("a paid-plan renewal didn't happen in time"), so sharing the field and functions is correct, not a coincidental reuse. The only genuinely new logic in the renewal lifecycle is: (a) the `sync_premium_renewals` command's own read of `premium_expires_at` to decide *when* to call those functions, and (b) clearing `premium_expires_at` after a failed-renewal downgrade, since spec 09's functions have no knowledge of that field.
- `CreatePremiumSubscriptionOrderView` needs no ownership mixin (`LockerOwnershipMixin`/`UserOwnershipMixin`) — it operates on `request.user`/`request.user.locker` directly with no object being looked up by a URL-supplied pk, the same shape `CreatePersonalShopPaymentOrderView` would have if it didn't take a `pk`. `LoginRequiredMixin` alone is the correct/sufficient guard, matching the existing `CreatePersonalShopPaymentOrderView`'s use of `LoginRequiredMixin` + `LockerOwnershipMixin` only because *that* view's URL takes an object pk — this one's doesn't.
- **`_activate_premium_subscription` must only ever run once per captured payment.** It is not naturally idempotent the way the existing `shipment`/`personal_shop_request`/`storage_batch` dispatch branches are — calling it twice for the same `Payment` extends `premium_expires_at` by 365 days a second time, a real revenue-affecting double-extension, not a cosmetic issue. `RazorpayWebhookView.post` already guards its whole dispatch chain with `if payment.status != 'captured':`; `VerifyPaymentView.post` did not have an equivalent guard before this spec and must gain one (see the `select_for_update()` change above) specifically because this spec introduces the first non-idempotent branch into that dispatch chain. This also incidentally hardens the pre-existing branches against the same double-fire risk, which is a welcome side effect, not the primary reason for the change.
